# 项目实验室 MVP 产品需求文档（PRD）

- 版本：v0.1
- 状态：基于产品讨论的已确认方案
- 产品模块：项目实验室
- 目标用户：初级项目经理、项目管理学习者、希望通过真实项目情境理解管理过程的用户

## 1. 产品定义

### 1.1 一句话定义

项目实验室是一个可回放的项目管理沙盘与情景推理训练工具：用户先观察一个成功项目的理想主线，再在关键节点接手项目、处理变式情景，最后将个人决策分支与理想主线对比复盘。

### 1.2 核心学习闭环

> 先看最优解，再做变式推理，最后与主线对比。

产品不把项目管理讲成孤立的知识点或标准答案选择题，而是让用户在项目经理的工作状态中观察信号、查阅文件、组合管理行动、承受行动后果，并理解不同管理动作在时间、成本、质量、风险、范围和干系人维度上的联动。

### 1.3 目标

1. 让无项目经验的学习者看懂一个项目从授权到收尾的关键管理过程。
2. 让用户理解项目文件、工具与技术、干系人、管理行动和仪表盘指标之间的关系。
3. 训练用户在不确定性下识别问题、选择必要管理动作并控制代价。
4. 通过理想主线与个人分支的差异，帮助用户形成“最小正确行动集合”的管理思路。
5. 复用现有知识库中的管理过程、项目文件、工具与技术、术语和关联关系。

### 1.4 非目标

1. MVP 不做通用项目管理软件，不提供真实项目的任务协作、审批流或多用户实时编辑。
2. MVP 不模拟所有行业和所有项目方法论；先完成一个完整、可复玩的教学案例。
3. MVP 不将 AI 作为项目结果的唯一裁判，不允许 AI 无依据改写规则引擎的项目结果。
4. MVP 不追求对真实项目的精确预测，而追求可解释、可复盘、符合项目管理逻辑的教学模拟。

## 2. 用户与使用场景

### 2.1 核心用户

| 用户 | 特征 | 核心诉求 |
|---|---|---|
| 初级项目经理 | 有基础概念，但缺少完整项目经验 | 看到各管理模块在实际项目中何时出现、如何联动 |
| 项目管理学习者 | 正在学习知识库、考试体系或方法论 | 把知识点转化为处理问题的思路 |
| 项目相关从业者 | 产品、研发、运营、测试等角色 | 理解项目经理为何要做文档、会议、变更和风险管理 |

### 2.2 典型用户旅程

1. 用户选择项目案例，进入项目主线回放。
2. 用户拖动项目时间轴，观察每个时点的仪表盘、里程碑、文件状态和历史版本。
3. 用户首次到达一个情景节点时，先查看理想主线的项目状态；节点随后解锁“从这里接手”。
4. 用户从节点创建个人分支，进入按周推进的回合制推演。
5. 用户从邮件、测试报告、消息、文件更新和仪表盘告警中发现问题。
6. 用户查看证据，组装行动链，填写决策依据并提交。
7. 系统推进一周，更新项目状态、图表、文件版本和待办；用户获得客观后果及缺口类别反馈。
8. 用户完成情景或走向结局后，查看个人分支与理想主线的对比，以及 AI 复盘。
9. 用户可以从任何已解锁的节点重新接手，保留旧分支并创建新的尝试。

## 3. MVP 范围

### 3.1 MVP 交付内容

1. 一个完整项目案例的 32 周主线回放。
2. 项目总进度时间轴、6 个里程碑和当前时点同步仪表盘。
3. 完整总览仪表盘、10 个管理领域入口与详细领域视图。
4. 始终可见的“项目经理抽屉”，可查看 32 份项目文件及其版本差异。
5. 3 个高价值情景节点和基于行动链的回合制推演。
6. 登录后云端保存个人分支、决策记录、状态快照、文件版本和 AI 复盘。
7. 理想主线与个人分支的 Git 式路径比较。
8. 知识库条目的原地侧栏联动。
9. 规则引擎驱动的客观后果与 AI 驱动的解释性评价。

### 3.2 首个项目案例

| 项目属性 | 已确认定义 |
|---|---|
| 案例名称 | 汽车手机端控制应用上线项目 |
| 项目类型 | 中型数字产品/移动应用项目，采用混合型生命周期 |
| 周期 | 8 个月，32 个周回合 |
| 核心团队 | 8 人 |
| 项目预算 | BAC（完工预算）260 万元 |
| 开发节奏 | 开发阶段两周一个迭代；推演以一周一个回合推进 |
| 外部依赖 | 车端接口供应商、安全测试方、试点车主代表 |
| 目标 | 在受控质量、安全和预算约束下完成 1.0 上线，并为后续功能迭代建立基础 |

### 3.3 1.0 产品范围

1. 账号登录、车主身份与车辆绑定。
2. 车辆状态查看：电量/油量、续航、车门与车锁状态、位置。
3. 远程控制：车门锁定/解锁、空调预设、车辆鸣笛/寻车。
4. 操作通知与操作记录。
5. 试点用户反馈入口。
6. 后台的用户、车辆、权限与运营监控。

明确不在 1.0 范围内：家庭成员共享车辆功能。该需求可在情景中被纳入 1.1 版本路线图。

### 3.4 项目质量与上线门槛

以下为教学案例基线，属于规则引擎中的硬质量/安全约束或关键成功条件：

| 指标 | 基线 |
|---|---:|
| 试点规模 | 300 名试点车主完成核心流程 |
| 车辆状态查询成功率 | 不低于 99% |
| 车辆状态查询 P95 响应时间 | 不高于 3 秒 |
| 远程控制指令成功率 | 不低于 98% |
| 远程控制审计 | 必须具备完整操作审计与撤销/失效机制 |
| 上线前安全风险 | 不存在未关闭的高危或严重安全漏洞 |
| 核心功能测试通过率 | 不低于 95% |
| 阻断级缺陷 | 0 个 |
| 试点用户满意度 | 不低于 4.2/5 |
| 服务可用性 | 不低于 99.5% |

## 4. 项目主线与里程碑

### 4.1 主线定位

主线不是唯一可接受的答案，而是满足必要管理动作、在正确时机以最小代价成功交付的理想路径。用户的合理替代路径可以成功，但会产生不同的时间、成本、范围或管理负担。

### 4.2 里程碑

| 周次 | 里程碑 | 主线关键产出 |
|---:|---|---|
| 第 0 周 | 项目授权 | 项目章程、初始干系人识别、初始风险识别 |
| 第 8 周 | 需求与范围基线 | 需求文件、WBS、进度基线、成本基线 |
| 第 12 周 | 方案与接口冻结 | 架构方案、车端接口范围、测试策略 |
| 第 20 周 | 核心开发完成 | 主要功能、集成准备、质量数据 |
| 第 28 周 | 试点验收 | 试点反馈、验收结论、上线准备 |
| 第 32 周 | 正式上线与复盘 | 最终交付、移交、经验教训 |

### 4.3 时间轴规则

1. 用户可拖动主线时间轴至任意已开放时点。
2. 拖动时间轴时，所有总览指标、管理领域数据、项目文件版本、待办和里程碑状态必须同步切换。
3. 某时点只能展示当时项目经理已知的事实、文件和状态；不得泄露未来发生的事件、结果或答案。
4. 关键情景节点显示“从这里接手”入口。
5. 首次进入某情景前，用户必须观看至该节点的理想主线；之后该节点永久解锁，可从该点创建任意数量的新分支。

## 5. 信息架构与页面结构

### 5.1 一级结构

1. 项目主线回放工作台。
2. 项目经理抽屉（32 项目文件）。
3. 管理领域详情页（10 大管理领域）。
4. 情景推演工作台。
5. 分支比较与 AI 复盘页。

### 5.2 主线回放工作台

主线回放工作台是产品默认入口，呈现最接近日常项目管理的状态仪表盘。

页面应包含：

1. 项目名称、当前周次、当前阶段、分支状态和保存状态。
2. 总项目进度条与 6 个里程碑。
3. 当前项目健康状态及总览仪表盘。
4. 情景节点入口及已解锁状态。
5. 10 个管理领域卡片。
6. 始终可见的项目经理抽屉入口。

### 5.3 总览仪表盘

总览仪表盘完整保留以下 15 项，不在 MVP 中因信息密度而删减。页面通过分区、折叠和下钻保证可读性。

#### 顶部：即时状态

1. 进度绩效指数 SPI。
2. 成本绩效指数 CPI。
3. 项目预算 BAC。
4. 项目实际花费 AC。
5. 项目工作量。
6. 干系人参与度。
7. CCB 待办项状态。

#### 中部：计划与交付

1. 里程碑甘特图。
2. 时标网络图。
3. WBS。
4. 当前迭代燃尽图。
5. 需求状态统计。

#### 右侧：风险与协作

1. 干系人 RACI 矩阵。
2. 风险影响-概率矩阵。
3. 风险状态统计。

#### 下部：领域入口

展示 10 个管理领域卡片：整合、范围、进度、成本、质量、资源、沟通、风险、采购、干系人。

每张卡片应显示当前状态摘要、关键异常、关联文件数和进入详情的入口。

### 5.4 管理领域详情

点击管理领域卡片后，展示：

1. 该领域的当前状态、历史趋势和详细图表。
2. 当前阶段关联的管理过程、工具与技术。
3. 该领域创建、引用或更新的项目文件。
4. 相关干系人、待办、风险、变更与决策记录。
5. 与其他管理领域的影响关系。

### 5.5 项目经理抽屉

抽屉是对“项目经理桌面文件系统”的具象化表达。

1. 入口在全局界面中始终可见。
2. 点击后进入独立文件浏览视图，可查看全部 32 份项目文件。
3. 每份文件展示当前状态、负责人、版本、更新时间、审批状态、创建/更新历史和内容。
4. 支持按当前阶段、管理领域、文件状态、是否本周更新进行筛选。
5. 打开文件时，高亮关联文档、关联仪表盘、相关管理领域与关联情景。
6. 从仪表盘异常、待办或情景材料进入文件时，应直接定位到相关版本或字段。

### 5.6 文件状态和版本差异

建议文件状态包括：未建立、草拟、评审中、已批准、已基线化、已更新、已归档。

版本视图采用类 Git 的表达方式：

1. 版本时间线显示谁在何时因何事修改了文件。
2. 内容差异明确标注新增、删除、修改。
3. 显示本次更新关联的事件、变更请求、风险、会议或管理行动。
4. 主线和个人分支中的文件版本可进行并排比较。

## 6. 32 份项目文件与知识库关系

MVP 采用现有知识库定义的 32 份项目文件作为抽屉的完整文件集合：

活动属性、活动清单、假设日志、估算依据、变更日志、成本估算、持续时间估算、问题日志、经验教训登记册、里程碑清单、物质资源分配单、项目日历、项目沟通记录、项目进度计划、项目进度网络图、项目范围说明书、项目团队派工单、质量控制测量结果、质量测量指标、质量报告、需求文件、需求跟踪矩阵、资源分解结构、资源日历、资源需求、风险登记册、风险报告、进度数据、进度预测、干系人登记册、团队章程、测试与评估文件。

现有知识库已经记录管理过程与文件之间的创建、引用、更新关系。MVP 应直接复用该关系，补充案例层面的周次、版本内容、审批状态和分支变化。

## 7. 情景推演设计

### 7.1 推演原则

1. 推演不以抽象弹窗直接宣布“风险事件”为主。
2. 问题通过日常材料呈现：供应商邮件、测试报告、干系人消息、会议邀请、文件新版本、项目仪表盘异常告警等。
3. 用户先发现信号，再判断问题并选择行动。
4. 第一版仅提供学习模式：系统提示“有需要关注的新信息”，并筛选当前场景相关的候选卡，但不直接公布正确组合。
5. 每回合用户必须填写决策依据后才能提交行动链。

### 7.2 回合制规则

1. 一个回合等于一个项目周。
2. 用户在一个回合内可查看当前可见的仪表盘、文件、邮件、消息和知识库条目。
3. 用户组装行动链、填写决策依据、提交后，系统自动推进一周。
4. 每周结算后更新项目状态、图表、风险、待办、文件版本和新信息。
5. 用户可以继续处理同一问题，也可能因未完全处理而触发衍生问题。
6. 推演中不采用现实时间倒计时，避免把学习压力错误地等同于项目时间压力。

### 7.3 三个 MVP 情景

#### 情景一：试点车主反馈引发的需求变更

| 属性 | 定义 |
|---|---|
| 发生时间 | 第 9 周，需求与范围基线之后 |
| 触发材料 | 试点车主代表的真实使用反馈邮件、需求状态异常、相关干系人消息 |
| 核心问题 | 用户提出家庭成员共享车辆功能，涉及多人授权、权限撤销和操作通知 |
| 影响领域 | 范围、整合、风险、沟通、干系人、进度、质量 |
| 理想主线 | 完整收集和澄清需求，评估安全/范围/进度/成本影响，提交 CCB 审查；将功能纳入 1.1 路线图，不改变 1.0 试点基线；向试点车主提供替代流程和明确承诺 |
| 教学重点 | 重视真实反馈，但不允许未经评估的需求冲击已批准基线 |

#### 情景二：供应商接口延期与核心工程师抽调

| 属性 | 定义 |
|---|---|
| 发生时间 | 第 17 周，核心开发期间 |
| 触发材料 | 车端接口供应商通知、接口问题记录、资源负荷告警、关键路径变化 |
| 核心问题 | 供应商接口安全网关问题导致交付预计延期 3 周；车端接口集成工程师同时被临时抽调处理线上生产事故 2 周 |
| 影响领域 | 进度、资源、采购、风险、质量、沟通、整合 |
| 理想主线 | 登记问题并复核关键路径和接口依赖；与供应商联合排障并确定最小可交付接口与分阶段日期；使用 Mock 接口并行完成可独立开发和测试的工作；安排可交接的备用工程师；持续更新风险、进度预测与供应商履约状态；真实接口恢复后完成集成验证 |
| 主线结果 | 以可控代价顺延 1 周，优先守住质量和集成验证标准 |
| 教学重点 | 合理的项目管理不等于绝不延期；先分析依赖和关键路径，再选择压缩或顺延策略 |

#### 情景三：试点前高危安全漏洞与上线窗口冲突

| 属性 | 定义 |
|---|---|
| 发生时间 | 第 25 周，试点验收前 |
| 触发材料 | 安全测试报告、质量告警、风险登记册更新、市场发布计划和试点车主消息 |
| 核心问题 | 远程控制鉴权存在高危漏洞，特定条件下可能越权执行车辆控制操作；既定上线窗口临近 |
| 影响领域 | 质量、风险、范围、沟通、干系人、进度、整合、采购 |
| 理想主线 | 不带风险开放远程控制；按期上线车辆状态查看等安全能力，临时关闭全部远程控制能力；更新范围、风险、测试、沟通和后续灰度开放计划 |
| 主线结果 | 按期完成安全可用的 1.0 分阶段上线，远程控制在漏洞修复、复测和灰度后开放 |
| 教学重点 | 安全红线不可用“按期上线”掩盖；通过范围裁剪和预期管理保护核心交付与用户安全 |

## 8. 行动链交互

### 8.1 目标

用户不只从多个文字选项中猜答案，而是像项目经理一样，将证据、工具、相关人员和落地行动组合成可执行的管理链。

### 8.2 卡片类型

| 卡片类型 | 作用 | 示例 |
|---|---|---|
| 证据文档卡 | 表示用户作为决策依据主动查阅并引用的文件 | 风险登记册、测试报告、需求跟踪矩阵 |
| 工具与技术卡 | 表示用于分析、协商、决策或审查的方法 | 头脑风暴、专家判断、会议、CCB 审查、备选方案分析 |
| 干系人卡 | 表示应参与、负责、被通知或被审批的角色 | 试点车主代表、产品负责人、发起人、供应商、安全负责人 |
| 执行行动卡 | 真正改变项目状态的操作 | 提交变更请求、建立 Mock 接口、调整计划、关闭远程控制、更新沟通计划 |

### 8.3 连接规则

推荐的行动链结构：

`证据文档` → `分析/决策工具` → `执行行动` → `相关干系人`

系统应允许一个行动关联多份证据、多项工具和多个干系人，但需限制为当前场景合理的连接关系，避免自由画布造成无意义组合。

### 8.4 文档的两种角色

1. **证据文档**由用户主动选择并连入行动链，代表用户判断有据可依。
2. **输出文档**由执行行动和管理过程自动生成或更新，代表项目管理工作留下可追溯记录。
3. 用户可在结算后查看输出文件的版本差异，并根据结果继续发起后续行动。

### 8.5 候选卡规模

学习模式下，每个情景提供 12–16 张候选卡：

1. 3–4 张证据/项目文件卡。
2. 3–4 张工具与技术卡。
3. 2–3 张干系人卡。
4. 4–5 张执行行动卡。

理想主线包含 5–7 个必要管理动作，映射为 8–14 张最小正确行动链卡片。候选项中应包含：

1. 必要且正确的动作。
2. 合理但非必要的冗余动作。
3. 时机错误或会引发负面后果的动作。

### 8.6 最小正确行动集合规则

1. 每个情景配置一组必要管理动作及其前置条件。
2. 用户遗漏必要动作时，风险不能完全闭环，对应指标会继续恶化或在后续回合引发问题。
3. 用户选齐必要动作时，风险得到控制，可回到主线或近主线路径。
4. 用户选择合理但非必要的动作时，项目可成功，但会消耗额外时间、成本、会议或管理资源，形成绕路支线。
5. 用户选择不当动作、跳过审批或忽略关键沟通时，可能产生延期、质量问题、预算损耗或失败分支。
6. 系统不得把“选得越多越好”作为正确策略；主线的目标是以最小正确集合完成处理。

### 8.7 决策依据

每回合提交行动链前，用户必须填写决策依据。输入框使用以下结构化提示：

1. 我观察到的关键信号是……
2. 我判断的主要风险/根因是……
3. 我选择这些行动的原因是……

该记录将自动写入个人分支的项目经理决策日志，作为最终 AI 复盘和主线差异比较的输入。

三个字段分别填写且全部必填，每项 20–500 字；支持引用用户已经查看的事件材料、项目文件和已选择行动卡，并显示为引用标签。系统自动保存草稿，未达到校验要求时禁止提交并在对应字段就地提示。系统不按关键词判分，不要求使用标准术语；AI 只评价文字判断与已查看证据、行动链及客观结果是否一致，避免把表达修饰程度误当作项目管理能力。

## 9. 即时反馈与结局复盘

### 9.1 当回合即时反馈

每次提交后，系统只展示客观后果和缺口类别，不直接给出具体正确卡片。反馈应包括：

1. 项目推进一周后的 SPI、CPI、AC、进度预测、风险和质量变化。
2. 甘特图、关键路径、工作量、燃尽图和相关领域图表变化。
3. 已创建或更新的项目文件及版本差异。
4. 新增邮件、消息、问题、风险或 CCB 待办。
5. 管理缺口类别，例如“风险已降低但未闭环：仍缺少审批、沟通或执行动作”。

同回合结算固定按照“提交校验→必要动作判断→正确行动局部效果→有害卡效果→未解决问题持续恶化→推进一周与计划事件→硬门槛和终局规则→重算图表与文件”的顺序执行。安全红线与失败条件优先级最高；成本和工作量累加，多个完工预测默认取最晚日期，风险采用仍有效的最高等级。一次性卡片效果在同一分支只结算一次；理想结果仅在完整满足近主线条件时整体应用，不能覆盖部分正确或有害行为。

### 9.2 情景结束复盘

情景结束后展示：

1. 用户行动链与理想主线最小正确集合的比较。
2. 漏掉的必要动作、冗余动作、时机问题和错误连接。
3. 路径偏离发生的周次及其累积影响。
4. 时间、成本、范围、质量、风险和干系人状态的差异。
5. 关联项目文件的版本差异。
6. AI 生成的解释性复盘。

路径对比采用 Git 式轨道：主线为灰色，每条个人分支使用独立颜色，每次回合提交形成不可修改节点，“从这里接手”为分叉点。点击节点可查看行动链、决策依据、状态变化和文件差异。第 1–32 周按同一日历周与主线快照比较，不按相同完成百分比比较；个人分支进入第 33 周后持续对比主线第 32 周最终快照，并标注“主线已完成”。最多同时叠加主线与 3 条个人分支；MVP 不支持合并或挑选节点，从历史节点重试会创建新分支并保留原路径。

### 9.3 最终结局等级

1. **理想成功**：完整范围、按期、预算与质量目标达成，且必要治理动作完整。
2. **受控成功**：通过合理范围裁剪或可解释代价完成核心目标。
3. **延期成功**：范围和质量达成，但超过原计划窗口。
4. **项目失败**：重大安全、质量、合规或核心目标未被控制，无法接受上线或交付。

## 10. 项目状态引擎

### 10.1 原则

项目状态不由单一总分或孤立图表决定。规则引擎维护项目的可解释状态，并将用户行动的前提、代价、时间与影响映射到多个维度。

### 10.2 状态维度

建议 MVP 至少维护以下状态维度：

1. 范围与需求状态。
2. 进度与关键路径状态。
3. 成本与预算状态。
4. 质量与安全状态。
5. 风险暴露与问题状态。
6. 资源与团队负荷状态。
7. 干系人参与和满意度状态。
8. 治理与项目文件完整性状态。

### 10.3 状态计算模型

1. 每个里程碑定义计划基线：日期、预算、范围、质量门槛、风险状态和文件状态。
2. 每个情景事件定义初始冲击：影响哪些状态维度、造成何种幅度的偏差、何时会恶化。
3. 每张行动卡定义前提条件、耗时、成本、作用对象、风险变化、文件更新和潜在副作用。
4. 每周结算根据当前状态、行动链和未解决问题生成新的状态快照。
5. 图表从状态快照派生，不直接作为评分源。
6. 硬门槛优先于一般指标。例如存在未关闭高危安全漏洞时，远程控制不得上线；即便 SPI、CPI 表现良好，也不能判定为成功。

### 10.4 结局判定顺序

1. 判断安全、合规、阻断级质量等硬门槛。
2. 判断核心范围和关键里程碑是否达成。
3. 判断进度、成本和资源偏差是否在可接受范围内。
4. 判断试点验收、干系人接受度和治理记录是否满足要求。
5. 输出结局等级与可解释原因。

## 11. AI 评价与知识库联动

AI 复盘不提供总分或用户排名，使用“表现成熟、仍在发展、需要练习”三级能力画像。评价维度固定为信号识别、风险与根因判断、行动完整性与最小性、时机与取舍、沟通与治理。输出必须包含做得好的地方、可改进点、与最优主线的关键差异、下次尝试建议和关联知识库内容；每条判断必须引用用户查看的材料、决策依据、行动卡、连接关系或客观项目结果。AI 不能推翻状态引擎给出的成功、延期或失败结论，只负责解释；服务不可用时仍完整展示规则复盘和路径差异。

### 11.1 AI 职责边界

规则引擎负责计算项目状态、行动后果和最终路径结果；AI 负责解释、追问、评价用户的管理思路，并识别符合约束的替代解法。

AI 不得：

1. 在没有规则依据时宣布用户失败或成功。
2. 覆盖安全、合规和质量硬门槛。
3. 凭空补充用户从未看见的项目事实。

### 11.2 AI 输入

1. 当前情景和已公开的证据材料。
2. 用户选择的行动链及连接关系。
3. 用户填写的决策依据。
4. 每回合状态变化、文件更新和项目事件日志。
5. 理想主线行动链与最小正确集合。
6. 用户个人分支与主线的差异。

### 11.3 AI 输出

AI 在情景结束或项目结束后生成复盘，包含：

1. 用户识别到的正确信号。
2. 用户遗漏的管理动作和造成的影响。
3. 用户使用的合理但额外动作及其代价。
4. 用户行动的时机、顺序和治理完整性评价。
5. 用户决策依据中体现的正确判断或误判。
6. 可接受的替代方案及其适用条件。
7. 推荐回看的知识库条目、工具技术和项目文件。

### 11.4 评价呈现

最终评价不显示单一总分，采用：

1. 路径结果等级。
2. 主线差异图。
3. 四项能力画像：信号识别、行动完整性、时机与代价、沟通与治理。
4. AI 文字复盘。
5. 从关键节点重新接手的入口。

### 11.5 知识库联动

推演中的工具、技术、文件和干系人卡均支持两层帮助：

1. 卡片内的一句场景化说明，解释该卡在当前问题中可能解决什么。
2. “查看依据”侧栏，打开知识库中的定义、适用条件、所属过程、关联文件和关联工具。

用户查看知识库时不离开项目工作台，不影响当前回合。

## 12. 分支、版本与云端保存

### 12.1 分支模型

1. 理想主线为只读基准路径。
2. 用户在任一已解锁情景节点点击“从这里接手”时创建个人分支。
3. 分支保留父节点、创建时间、每周行动、决策依据、状态快照、文件版本和结局。
4. 用户可以从任意已解锁节点再次创建分支，不覆盖旧分支。
5. 比较界面可选择理想主线、一个或多个个人分支进行并排比较。

### 12.2 保存范围

登录后云端保存：

1. 已解锁节点。
2. 个人分支关系。
3. 每回合行动链和决策依据。
4. 每周项目状态快照。
5. 分支内文件版本与版本差异。
6. 结局结果、能力画像和 AI 复盘。

### 12.3 MVP 权限边界

1. 用户默认只能查看和编辑自己的分支。
2. 理想主线及其基础案例数据只读。
3. MVP 不做分支分享、协作编辑、排行榜或公开评价。

## 13. 核心用户故事

1. 作为学习者，我希望拖动主线时间轴查看项目不同阶段的状态，以理解项目管理工作何时发生。
2. 作为学习者，我希望看到仪表盘和项目文件在同一时点同步变化，以理解数据与文档之间的关系。
3. 作为学习者，我希望从真实材料发现问题，而不是直接看到答案，以训练项目经理的判断。
4. 作为学习者，我希望将文件、工具、干系人与行动连接起来，以模拟真实的项目处理思路。
5. 作为学习者，我希望每周看到行动后果，但不立即被告知标准答案，以保留推理空间。
6. 作为学习者，我希望在结局后看到与主线的具体差异，以理解自己在哪里绕路、延期或失败。
7. 作为学习者，我希望能够从同一节点多次尝试，以比较不同管理策略。
8. 作为学习者，我希望从卡片直接查看知识库依据，以在实践中掌握工具与技术。
9. 作为学习者，我希望保存自己的路径和复盘结果，以形成长期学习记录。

## 14. 验收标准

### 14.1 主线回放

1. 用户可在 0–32 周之间拖动时间轴。
2. 时间点切换后，仪表盘、文件状态、里程碑、待办和领域卡片同步更新。
3. 用户无法在第 N 周看到第 N+1 周才公开的事件或文件内容。
4. 6 个里程碑均可在时间轴中识别，且显示状态和关联产出。

### 14.2 仪表盘和文件抽屉

1. 总览可展示 15 项已确认指标/图表。
2. 10 个管理领域均有可进入的详情入口。
3. 抽屉可浏览全部 32 份文件。
4. 文件支持状态、历史、版本差异和关联关系查看。
5. 从文件可定位关联仪表盘/领域；从异常指标可定位关联文件。

### 14.3 情景推演

1. 三个情景节点分别位于第 9、17、25 周。
2. 用户首次到达节点前不能直接开始推演；完成主线观察后可解锁。
3. 每个情景以邮件、报告、消息、文件或告警的组合方式呈现问题。
4. 每个情景提供 18–24 张相关候选卡，包含 5–7 个必要管理动作，并存在由 8–14 张卡构成的最小正确行动链。
5. 用户未填写决策依据时不能提交行动链。
6. 提交后项目推进一周，并产生可观察的状态、文件和消息变化。
7. 即时反馈只显示客观后果和缺口类别，不直接显示正确卡片。
8. 情景结束后可查看行动链比较和 AI 复盘。

### 14.4 分支与评价

1. 用户可以从任意已解锁节点创建多个独立分支。
2. 旧分支不会被新尝试覆盖。
3. 分支比较至少展示分叉点、周次、主要状态差异、结局和文件差异。
4. 评价至少包含结果等级、四项能力画像和 AI 复盘。
5. AI 评价中的事实必须可追溯至用户行动、项目材料或规则引擎状态。

### 14.5 保存与知识库

1. 登录用户重新进入后可恢复分支与当前进度。
2. 每张工具、技术、文件与干系人卡可打开知识库侧栏说明。
3. 知识库侧栏不丢失当前推演回合的上下文。

## 15. 案例数据配置项（后续内容制作）

以下内容不应在页面组件中硬编码，应以案例配置数据管理：

1. 32 周主线的状态快照和全部仪表盘数值。
2. 6 个里程碑的计划、实际、审批和文件基线状态。
3. 32 份文件的创建周次、更新周次、负责人、版本内容和差异。
4. 三个情景的触发材料、候选卡、可见线索、必要管理动作和最小正确集合。
5. 每张行动卡的前提、耗时、成本、状态影响、文件更新和副作用。
6. 每个情景的合理冗余动作、不当动作、衍生事件与结局路径。
7. AI 复盘模板、能力画像规则和知识库推荐映射。
8. 图表的初始值、基线、预警阈值和展示文案。

## 16. 后续迭代方向（非 MVP）

1. 新增更多行业案例：会员点单小程序、企业系统实施、BIM 智慧审查平台等。
2. 增加标准模式和挑战模式，逐步移除候选筛选和提醒。
3. 支持用户在推演中撰写更完整的变更请求、风险应对方案或会议纪要。
4. 支持案例作者工具，以配置新项目、情景、行动卡和状态规则。
5. 支持分支分享、导师点评、学习报告和组织培训场景。
6. 增加跨情景的长期项目组合学习路径。
